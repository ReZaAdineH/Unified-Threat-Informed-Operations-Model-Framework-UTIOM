# Community and Contribution

The UTIOM Ecosystem is intended to improve through practitioner experience, transparent challenge and evidence.

The community is not only a promotion channel. It is part of the improvement mechanism for UTIOM, TID-CMM, TIR-CMM and related public ecosystem components.

## Where conversation happens

### Slack

Slack is the fast collaboration layer for:

- practitioner conversation;
- implementation questions;
- working discussions;
- early ideas;
- research collaboration;
- relationship-building across the ecosystem.

The Slack workspace is organised around the ecosystem rather than separate workspaces for each model.

Current channel structure includes:

- `#all-utiom-ecosystem`
- `#utiom`
- `#tid-cmm`
- `#tir-cmm`
- `#community-contributions`
- `#social`

### GitHub

GitHub is the durable public layer for:

- versioned documentation;
- Issues;
- Discussions where enabled;
- Pull Requests;
- implementation stories;
- model challenges;
- standards mappings;
- evidence-backed proposals;
- public changelogs.

## Working rule

> **Slack is for conversation. GitHub is where durable knowledge, evidence and accepted framework changes live.**

A useful Slack discussion should move to the relevant GitHub repository when it produces something that should remain public, reviewable and versioned.

## What good contributions look like

Useful contributions include:

- a counter-example showing that a descriptor or model assumption does not match operational reality;
- a real implementation story from an internal, outsourced, hybrid, cloud or OT/ICS environment;
- a telemetry or detection-validation lesson;
- evidence about decision latency or containment performance;
- a standards or regulatory crosswalk;
- a clarification that makes a framework concept easier to implement without changing its meaning;
- an anonymised measurement that helps calibrate a maturity model;
- a proposal for a new ecosystem component with a clear role and evidence that it solves a distinct problem.

## Governance

Open participation does not mean uncontrolled framework design.

The canonical UTIOM lifecycle, pillars and core architecture are maintained deliberately. Supporting models have their own versioning and governance. Proposed changes should explain the problem, evidence and operational consequence rather than relying on preference alone.

## Security and sensitive information

Do not publish:

- credentials or secrets;
- private production architecture;
- customer data;
- sensitive incident data;
- confidential assessment results;
- exploitable vulnerability details before coordinated disclosure.

Use the `SECURITY.md` policy in the relevant repository for suspected vulnerabilities.
