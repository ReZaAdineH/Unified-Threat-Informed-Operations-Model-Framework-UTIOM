# UTIOM Community

UTIOM is an open, living framework. The community exists to improve the framework through transparent sharing, practitioner experience, peer review and evidence-backed challenge while preserving the canonical UTIOM architecture and philosophy.

## Community purpose

The UTIOM community is for practitioners, researchers, architects, SOC leaders, detection engineers, incident responders, threat-intelligence professionals, security engineers, auditors and educators who want to improve how security operations are designed, measured and continuously improved.

The community should help answer practical questions such as:

- How can UTIOM be applied to build a SOC from scratch?
- How can an existing SOC use UTIOM to identify and prioritise capability gaps?
- How should Threat Profiling, Crown Jewels, threat modelling and attack paths drive telemetry and detection requirements?
- How should Telemetry Engineering and Detection Engineering be validated?
- How can Response Horizon, prepared authority and response engineering improve operational outcomes?
- Which metrics demonstrate real capability and risk reduction rather than activity volume?
- How should UTIOM map to MITRE ATT&CK, NIST, ISO, NIS2, DORA, SOC-CMM and other established models without being redefined by them?

## Ways to participate

### 1. Share implementation experience

Tell the community how you applied UTIOM in a real or lab environment, what worked, what did not, which dependencies became visible and what you changed as a result.

### 2. Propose improvements

Open an issue for corrections, clarifications, mappings, examples, diagrams, assessment improvements or implementation guidance.

### 3. Contribute evidence

UTIOM should improve through evidence rather than opinion alone. Useful contributions include:

- operational lessons;
- measurable outcomes;
- validation results;
- detection and telemetry engineering lessons;
- incident-response exercises;
- standards mappings;
- research and references;
- constructive criticism of assumptions or terminology.

### 4. Contribute examples

Community examples are welcome for internal, outsourced and hybrid SOCs, as well as cloud, financial services, enterprise, OT/ICS and other environments.

### 5. Review public releases

Community members are encouraged to review new public releases, assessments, diagrams and mappings and identify ambiguity, missing evidence or implementation challenges.

## Quarterly Kaizen community review

UTIOM uses continuous improvement as a core principle, so the community should follow the same approach.

A quarterly community review should collect:

1. important practitioner feedback;
2. documentation corrections;
3. implementation lessons;
4. assessment and metrics feedback;
5. mapping updates;
6. validation findings;
7. prioritised public improvement proposals.

The purpose is not to change the framework for the sake of change. Improvements should strengthen clarity, traceability, usability and evidence while remaining loyal to the canonical UTIOM model.

## Canonical architecture

Community participation does not mean that the core model can be silently redefined.

The seven canonical UTIOM phases remain:

**Vision → Strategy → Crown Jewels → Threat Visibility → Threat Detection → Response → Continuous Improvement**

The three canonical pillars remain:

- **Leadership & Governance**
- **Engineering & Enablement**
- **Operations & Analysis**

The model has ordered dependencies with iterative engineering and operational feedback loops. Contributions may clarify, validate, map and extend implementation guidance, but changes to canonical doctrine remain maintainer-governed.

## Community principles

- Be constructive and evidence-led.
- Challenge ideas, not people.
- Prefer operational reality over framework theatre.
- Share enough context for others to learn from the contribution.
- Respect confidential, customer and production information.
- Do not publish credentials, private infrastructure details or sensitive assessment data.
- Attribute external sources and prior work appropriately.
- Keep the public/community edition separate from private or future commercial implementation material.
